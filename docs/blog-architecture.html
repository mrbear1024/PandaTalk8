Technical Architecture

PandaTalk8 博客文章发布技术方案

支持 HTML 预渲染和 Markdown 动态渲染的双格式架构，从写入到展示的完整数据流

TL;DR 数据库 body 列同时兼容四种格式：HTML string 预渲染正文片段、Markdown string 原始内容、Block[] 结构化块，以及 HTML document 完整 HTML 文档。页面渲染层根据 body_format 自动分支——正文片段进入站点文章模板，完整 HTML 文档从文章 URL 直接跳转到原始 HTML document route，像本地打开 HTML 文件一样展示。

01数据库存储：body 列的四种格式

Supabase posts 表的 body 列类型为 jsonb，实际存储的是一个 JSON 值。由于历史演进和功能需求，这个值有四种合法形态：

HTML String 当前主力

正文 HTML 片段，例如 <p>...</p>。后台富文本和 Markdown 预渲染默认走这个格式。读取时进入站点文章模板，仅做代码高亮。

Markdown String 新增支持

直接存原始 Markdown 内容。读取时在服务端动态调用 Markdown 渲染器转为 HTML，再做代码高亮后输出。

HTML Document 新增支持

完整 HTML 文档，例如包含 <html>、<head>、<style>、<body> 的独立页面。读取时不进入 .prose，而是通过 document 路由直接返回原始 HTML。

Block Array 历史遗留

早期格式，body 是 [{type:"h1",text:"..."}, {type:"p",text:"..."}] 结构化数组。页面逐块映射为 React 元素。

格式检测逻辑

function detectBodyFormat(body, body_format): "html" | "markdown" | "html_document" | "blocks"

  if body_format is set
    return body_format       // 推荐：显式标记，零猜测

  if Array.isArray(body)
    return "blocks"          // 历史遗留的结构化块

  if typeof body === "string"
    if body contains "<!doctype" or "<html" or "<head"
      return "html_document" // 完整 HTML 文档
    if body contains "<p>" or "<h1>" or "<div>" ...
      return "html"          // 已渲染的 HTML
    else
      return "markdown"      // 原始 Markdown
推荐：显式标记。在 posts 表新增 body_format 列（枚举：'html' | 'md' | 'blocks' | 'html_document'），写入时明确标记，读取时零猜测。比内容嗅探更可靠，尤其对于不含任何 HTML 标签的纯文本段落，以及包含完整 <html> 结构的文档页面。

A 预渲染入库（当前）

CLI 提交 body_md → 服务端 marked.parse() 转为 HTML → 存入 body 列。
优点：读取时零额外计算。
缺点：原始 Markdown 丢失，无法再次编辑源码。

or

B Markdown 原样入库（新增）

CLI 提交 body_md + body_format: "md" → 服务端直接保存原始 Markdown 到 body 列。
优点：保留源码，支持再次编辑、格式切换。
代价：每次读取需动态渲染。

HTML fragment 与完整 HTML document 必须区分。 当前后台富文本和 Markdown 预渲染产物只是正文片段，适合放进站点的 .prose 容器。像 docs/blog-architecture.html 这种完整 HTML 文档包含自己的 <head>、<style>、<body>，不能直接塞进文章正文容器，否则会产生非法 DOM、样式互相污染和安全边界不清晰的问题。

C 完整 HTML 文档入库（新增）

CLI/API 提交 body_html + body_format: "html_document" → 服务端原样保存完整 HTML 到 body 列。
读取时 /blog/<slug> 直接跳转到 /blog/<slug>/document，由该路由返回完整 HTML 文档。

safe boundary

安全与兼容边界

站内文章模板不注入完整 HTML 文档；document 路由直接返回 text/html。这样 HTML 文档可以保留自己的样式和布局，同时不会影响导航栏、页脚、文章列表、RSS 和现有富文本文章。

03读取流程：格式感知的渲染管线

访客请求 /blog/some-slug 时，服务端从 Supabase 取出 post.body，根据格式走不同的渲染分支：

   detectBodyFormat(post.body)

    │      │                  │
    │      └────────┬─────────┘

    │               ▼

    <H1> / <H2> / <P> …)

    │                               redirect("/blog/<slug>/document")

                   ▼
           完整 HTML 页面返回浏览器

渲染分支详解

格式 检测条件 渲染步骤 开销
HTML typeof body === "string" 且含 HTML 标签 highlightCodeBlocks → dangerouslySetInnerHTML 低：仅正则替换代码块
Markdown typeof body === "string" 且不含 HTML 标签（或 body_format === "md"） marked.parse → highlightCodeBlocks → dangerouslySetInnerHTML 中：Markdown 解析 + 代码高亮
HTML Document body_format === "html_document" /blog/[slug] redirect → /blog/[slug]/document 原样返回完整 HTML 低：主页面无解析；document route 直接输出
Blocks Array.isArray(body) 逐块 .map() 映射为 React 元素 低：无解析，直接映射
Markdown 动态渲染的性能影响。 marked.parse() 对一篇 3000 字的文章耗时约 1-3ms（Node.js 服务端），加上代码高亮约 5-10ms。对比完整 SSR 的 200-500ms 总耗时，额外开销可忽略。且这个计算发生在服务端 Server Component 内，不增加客户端 JS bundle。

06page.tsx 渲染伪代码

// app/(site)/blog/[slug]/page.tsx — 渲染逻辑

import { marked } from "marked";
import { highlightCodeBlocks } from "@/lib/highlight";

function renderBody(post) {

  // 分支 0: 完整 HTML 文档（新增）
  if (post.body_format === "html_document") {
    redirect(`/blog/${post.slug}/document`);
  }

  // 分支 1: Block 数组（历史遗留）
  if (Array.isArray(post.body)) {
    return post.body.map(block =>
      block.type === "h1" ? <h1>{block.text}</h1>
      block.type === "p"  ? <p>{block.text}</p>
      ...
    );
  }

  // 分支 2: 字符串内容（HTML fragment 或 Markdown）
  if (typeof post.body === "string") {

    let html = post.body;

    // 2a: 如果是 Markdown，先动态渲染为 HTML
    if (post.body_format === "md" || !looksLikeHtml(post.body)) {
      html = marked.parse(post.body);
    }

    // 2b: 代码高亮（对 HTML 和 Markdown→HTML 都生效）
    html = highlightCodeBlocks(html);

    return <div dangerouslySetInnerHTML={{ __html: html }} />;
  }

  return null;
}

完整 HTML 文档输出路由伪代码

// app/(site)/blog/[slug]/document/route.ts — 独立文档输出

export async function GET(request, { params }) {
  const post = await getPost(decodeSlug(params.slug));

  if (!post || post.body_format !== "html_document") {
    return new Response("Not found", { status: 404 });
  }

  if (typeof post.body !== "string") {
    return new Response("Invalid document", { status: 500 });
  }

  return new Response(post.body, {
    headers: {
      "content-type": "text/html; charset=utf-8",
      "x-robots-tag": "noindex"
    }
  });
}
为什么 document 路由建议 noindex？ SEO、OG、RSS、站内导航仍可指向 /blog/[slug]，它会跳转到原始 HTML 输出。若希望裸文档页面避免重复收录，可以在 /blog/[slug]/document 上保留 x-robots-tag: noindex；若未来希望 HTML 文档本身被搜索引擎收录，则需要为 document route 单独设计 canonical 与元信息策略。

07方案对比与选择

写入策略对比

指标 预渲染入库 (HTML) 原样入库 (Markdown)
读取性能 最优，HTML 直出 略慢 ~3-10ms（Markdown 解析）
源码保留 丢失 Markdown 原文 完整保留，可再编辑
渲染一致性 写入时锁定渲染结果 随渲染器升级自动更新样式
存储体积 HTML 比 Markdown 大 ~1.5-2x 更紧凑
全站样式更新 需重新渲染所有文章 自动生效

页面渲染模式对比

当前：force-dynamic SSR

每次访问查 DB + 渲染，延迟 ~200-500ms。数据实时可见。每个 PV 都查一次 Supabase。简单粗暴，无缓存。

可选：ISR 增量静态再生成

命中缓存时 ~0ms（CDN 直出）。写入后通过 revalidatePath 刷新，延迟 <1s。只在缓存失效时查 DB。去掉 force-dynamic 即可。

指标 force-dynamic (当前) ISR (可优化)
首次访问延迟 ~200-500ms ~0ms (CDN 命中)
数据新鲜度 实时 写入后 <1s 可见
Supabase 负载 每 PV 一次查询 仅缓存失效时查询
Markdown 渲染开销 每请求都算一次 缓存失效时才算
改动量 — 删除 3 行 force-dynamic
推荐组合。 Markdown 原样入库 + ISR 是最优组合：Markdown 的动态渲染开销（~5ms）被 ISR 的缓存层完全吸收——只有缓存 miss 时才执行一次，后续访问全部由 CDN 静态页面直出。既保留了 Markdown 源码的可编辑性，又获得了接近零延迟的访问速度。

08实施路径

  1. 数据库：新增 body_format 列
    ALTER TABLE posts ADD COLUMN body_format text NOT NULL DEFAULT 'html';
    合法值：'html'、'md'、'blocks'、'html_document'。存量数据全部默认为 'html'，历史 Block[] 可通过读取时嗅探继续兼容，不需要立即迁移。
  2. posts-service.ts：写入分支
    当请求携带 body_format: "md" 时，跳过 marked.parse()，将 Markdown 原文直接存入 body 列，同时写入 body_format = 'md'。当请求携带 body_format: "html_document" 时，要求提交 body_html，并原样保存完整 HTML 文档。
  3. page.tsx：渲染分支
    读取 post.body_format：'md' 在服务端调用 marked.parse() 后再走代码高亮；'html_document' 不进入 .prose，而是从 /blog/[slug] 直接跳转到 /blog/[slug]/document。
  4. document 路由：隔离完整 HTML
    新增 app/(site)/blog/[slug]/document/route.ts，只允许 body_format = 'html_document' 的文章返回完整 HTML。响应头使用 text/html; charset=utf-8，并建议添加 x-robots-tag: noindex，避免重复收录。
  5. CLI：新增 --raw 开关
    node blog.mjs publish article.md --raw 将 Markdown 原样提交，不经过服务端预渲染。默认行为不变（仍预渲染为 HTML）。
  6. CLI/API：新增 HTML document 发布模式
    node blog.mjs publish-html docs/blog-architecture.html --title "PandaTalk8 博客文章发布技术方案" 或 HTTP API 提交 { body_html, body_format: "html_document" }。第一阶段只支持可信管理员/API 发布，不进入富文本编辑器。
  7. 可选：去掉 force-dynamic，启用 ISR
    删除页面中的 export const dynamic = "force-dynamic"，利用已有的 generateStaticParams + revalidatePath 获得 CDN 级性能。

10结论

这套方案的核心设计是存储格式与渲染解耦：数据库的 body 列可以存任意格式的内容，页面渲染层通过 body_format 标记（或内容嗅探）自动选择对应的渲染管线。

对于 Markdown 内容，渲染发生在 Next.js 的 Server Component 内（服务端），不增加客户端 JavaScript 体积。配合 ISR 缓存后，Markdown 的动态渲染开销只在缓存失效时产生一次，后续请求全部由 CDN 直出静态页面。

完整 HTML 文档不应该被当成正文片段注入现有文章模板，而应该通过独立 document 路由直接输出。这样既能保留技术文档、报告、可视化页面自己的 CSS 与布局，又不会破坏主站导航、页脚、文章样式、RSS 和 OG 卡片。

这使得博客系统同时具备了：HTML 正文片段的零开销直出、Markdown 内容的动态渲染与源码可编辑性、完整 HTML 文档的隔离发布能力、历史 Block 格式的向后兼容——四种格式在同一套发布与渲染管线中无缝共存。
